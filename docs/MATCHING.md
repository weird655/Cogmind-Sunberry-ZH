# 匹配策略：现状与后续目标

本文区分现有实现与建议目标；稳定文本编号体系和覆盖总账尚未全部实现。

## 什么匹配更合适

有可靠文本编号时，优先使用“资源类别＋记录编号＋字段＋上下文”，并验证原文摘要。跨游戏版本需建立编号对应关系，不能把解压偏移、EXE 地址或行号当成永远稳定的编号。

没有编号时，优先使用完整英文原文精确匹配，再进行受限的格式规范化匹配。动态文本使用明确的句式和带类型变量，名称、数字、坐标与链接编号分别保留。最后才考虑人工核对的别名。

模糊匹配用于离线寻找疑似对应项，不默认用于运行时替换。找到相近句子不证明语义一致；否定词、物品等级、数量和链接对象尤其容易误配。候选冲突应保留英文并记录原因。

现有译表含英文键；其部分内容来自韩文化包，不意味着运行时应拿韩文匹配英文画面。来源与许可是另一项元数据，不能由匹配成功推导出授权。

## 三类职责

- 文本解析：输入原文与语义类别，输出译文、规则及失败原因，不触碰游戏对象。
- 界面适配：负责取得完整原文、列宽、颜色、链接、对象生命周期和切换显示。
- 版本适配：核验 EXE 和数据库，提供已验证的地址及对象布局，未知版本保留英文。

当前第一层已有共享解析与四种 profile；后两层仍依赖固定版本地址、调用位置和部分共享状态。它是可用的专用适配器，尚非完全解耦的通用本地化接口。

## 为什么换算法还会漏译

翻译函数只能处理送到它的文字。某个弹窗绕过该函数，或标题在送入前已被裁切，单独扩大词典无法解决。需要在经过验证的边界接入完整文本，不能任意改写游戏内部的所有字符串缓冲区。

## 覆盖总账建议字段

来源文件、版本、记录类别、记录编号、字段、原文摘要、原文、目标文字、译文来源、匹配结果、显示入口、画面验证状态。

“表内有译文”“匹配成功”“接口接通”“画面正确”分别记录；不能用表内行数或一次正常启动代替全局覆盖率。文件偏移作为溯源证据保留，而非跨版本身份标识。
